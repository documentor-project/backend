# 문서 데이터 처리 경험에서 RAG 서비스 고도화까지

## 1. 경험의 출발점

LG전자와 함께한 프로젝트에서 PDF 문서를 Markdown(MD) 문서로 변환해 LLM이 활용할 수 있는 형태의 데이터로 정리하는 작업을 수행했다. 이 경험을 통해 비정형 문서를 단순 텍스트로 추출하는 것만으로는 충분하지 않다는 점을 배웠다.

PDF에는 제목, 문단, 표, 코드 블록, 페이지와 같은 구조적 정보가 섞여 있다. 변환 과정에서 이러한 맥락이 손실되면 LLM이 문서의 의미를 잘못 이해하거나, 필요한 정보를 찾지 못할 수 있다. 따라서 AI 서비스의 품질은 모델 호출 자체뿐 아니라 입력 데이터의 구조화와 검색 정확도에 크게 좌우된다는 문제의식을 갖게 되었다.

## 2. 문제의식을 서비스로 확장한 이유

문서 데이터를 LLM에 활용 가능한 형태로 만들었던 경험을 바탕으로, 사용자가 업로드한 기술 문서에서 면접 질문을 생성하는 RAG 서비스인 DocuMentor를 기획하고 구현했다.

DocuMentor는 PDF, Markdown, TXT 문서를 업로드하면 문서를 청크로 분할하고 임베딩한 뒤, 사용자가 선택한 직무 분야·난이도·질문 유형에 맞춰 근거 기반 기술면접 질문과 꼬리질문을 생성한다. 생성된 질문에는 출처 문서와 페이지 정보를 함께 제공해 사용자가 질문의 근거를 확인할 수 있도록 설계했다.

## 3. 초기 구현

초기 파이프라인은 다음 흐름으로 구성했다.

```text
문서 업로드
  -> 텍스트 추출(PDF / MD / TXT)
  -> 청크 분할 및 메타데이터 부여
  -> 임베딩 및 벡터 저장
  -> 사용자 조건 기반 검색
  -> LLM 질문 및 꼬리질문 생성
  -> 질문과 출처 제공
```

이를 통해 문서 기반 질문 생성이라는 핵심 기능을 구현했지만, 실제 서비스 관점에서 다음과 같은 한계도 확인했다.

## 4. 발견한 문제와 개선 방향

| 구분 | 발견한 문제 | 원인 가설 | 개선 방향 | 검증 지표 |
|---|---|---|---|---|
| 청킹 | 문서 구조가 반영되지 않은 청크는 질문의 근거가 부족하거나 문맥이 끊길 수 있음 | 동일한 토큰 기준 분할은 제목·문단·코드 블록·표의 의미 경계를 고려하지 못함 | 문서 유형별 분할, 제목 기반 시맨틱 청킹, 코드 블록 보존, 적절한 overlap 적용 | 정답 근거 포함 청크 비율, 출처 일치율 |
| 검색 | 사용자의 조건만 조합한 검색 질의는 실제 질문 의도와 거리가 있을 수 있음 | 분야·난이도·질문 유형이 검색 질의에 충분한 의미를 제공하지 못함 | 질의 재작성, top-K·유사도 임계값 실험, 중복 제거, reranking 검토 | Recall@K, 중복 청크 비율, 생성 실패율 |
| 벡터 저장 | 인메모리 벡터 저장소는 서버 재시작 후 검색 인덱스가 유지되지 않음 | 벡터 데이터가 애플리케이션 메모리에만 존재함 | pgvector 또는 Qdrant 등 영속 벡터 저장소 도입, 문서 삭제 시 벡터 삭제, 재색인 기능 | 재시작 후 검색 성공률, 고아 벡터 수 |
| 작업 관리 | 질문 생성 진행 상태가 메모리에 있어 재시작 시 작업 이력이 사라질 수 있음 | 작업 상태를 DB가 아닌 ConcurrentHashMap으로 관리함 | 생성 작업 Job 테이블, 상태·실패 사유·재시도 횟수 저장, 재시도 API 제공 | 재시작 후 상태 보존율, 실패 원인 추적률 |
| 품질 평가 | 생성된 질문이 실제 문서 근거에 충실한지 정량적으로 판단하기 어려움 | 평가용 데이터셋과 기준이 없음 | Golden dataset 구성, 근거성·난이도 적합성·중복률·질문 유형 일치율 평가 | groundedness, 난이도 적합률, 중복 질문 비율 |

## 5. 현재 코드에서 확인한 근거

다음 내용은 프로젝트 구현을 바탕으로 정리한 사실이다.

- 벡터 저장소는 `SimpleVectorStore` 기반으로 구성되어 있어, 현재 구조에서는 서버 재시작 이후 벡터 데이터 영속성을 보장하기 어렵다.
- 문서 청킹에는 기본 `TokenTextSplitter`를 사용하고 있어 문서 구조별 분할 전략을 적용할 여지가 있다.
- 검색 질의는 분야, 난이도, 질문 유형을 결합한 형태이며, 질의 재작성이나 reranking은 아직 적용되어 있지 않다.
- 질문 생성 상태는 메모리 기반 자료구조로 관리되므로 작업 이력과 실패 사유를 영속적으로 관리하는 개선이 가능하다.
- 문서 근거 기반 질문 생성 프롬프트와 출처 정보 제공은 이미 구현되어 있어, 이후 품질 평가 체계를 붙이기 좋은 기반이 있다.

## 6. 개선 실행 순서

1. 평가 기준과 Golden dataset을 먼저 정의한다.
   - 개선 전후를 비교할 수 있도록 대표 문서와 예상 질문·근거 청크를 준비한다.
   - Recall@K, 근거 일치율, 중복 질문 비율을 측정한다.

2. 문서 구조 기반 청킹을 적용한다.
   - Markdown은 heading 단위, PDF는 페이지·문단 정보, 기술 문서는 코드 블록 경계를 보존한다.
   - 청크 메타데이터에 문서 ID, 사용자 ID, 페이지, 섹션 제목, 청크 순서를 저장한다.

3. 검색 품질을 개선한다.
   - 사용자 조건을 검색용 질의로 재구성한다.
   - top-K와 유사도 임계값을 실험하고, 중복 청크 제거 및 reranking을 적용한다.

4. 운영 가능한 저장·작업 구조로 전환한다.
   - 영속 벡터 저장소를 도입하고 문서 삭제·재색인 흐름을 구현한다.
   - 질문 생성 Job을 DB로 관리해 상태, 실패 사유, 재시도 이력을 보존한다.

5. 결과를 지표와 실패 사례로 검증한다.
   - 개선 전후 동일한 평가셋으로 검색 결과와 생성 질문을 비교한다.
   - 잘못된 출처, 중복 질문, 난이도 불일치 사례를 기록하고 원인과 조치 내용을 남긴다.

## 7. 자소서용 서술 초안

### 문제 해결 중심

LG전자 협업 프로젝트에서 PDF 문서를 Markdown으로 구조화해 LLM 활용 데이터를 만드는 작업을 수행했습니다. 이 과정에서 단순 텍스트 변환만으로는 문서의 제목, 문단, 코드 블록 등 맥락이 손실되어 AI 활용 품질이 낮아질 수 있음을 경험했습니다. 이후 이 문제의식을 확장해 문서 기반 기술면접 질문 생성 RAG 서비스 DocuMentor를 기획·개발했습니다. 초기 구현 후 청킹, 검색, 벡터 저장, 작업 상태 관리 단계의 한계를 분석하고, 평가 지표를 기반으로 품질과 운영 안정성을 개선하는 방향을 설계했습니다.

### 기술 딥다이브 중심

RAG 서비스에서 LLM의 생성 품질은 프롬프트뿐 아니라 검색된 컨텍스트의 품질에 좌우된다고 판단했습니다. DocuMentor의 기본 토큰 단위 청킹과 조건 조합형 검색 질의를 분석한 뒤, 문서 구조 기반 청킹, 검색 질의 재작성, Recall@K 및 근거 일치율 측정 체계를 개선 과제로 정의했습니다. 이를 통해 AI 기능을 단순 API 연동이 아닌 데이터 전처리·검색·생성·평가가 연결된 파이프라인으로 바라보는 관점을 갖추었습니다.

### 백엔드·운영 중심

문서 임베딩과 질문 생성 기능을 구현한 뒤, 인메모리 벡터 저장소와 메모리 기반 작업 상태 관리가 서버 재시작 시 데이터와 작업 이력을 보존하지 못한다는 운영상 한계를 발견했습니다. 이에 영속 벡터 저장소 도입, 문서 삭제 시 벡터 정합성 보장, 생성 Job의 DB 기반 상태 관리와 재시도 정책을 개선 방향으로 설계했습니다. 기능 구현 이후에도 장애 추적과 데이터 지속성을 고려하는 백엔드 설계 역량을 키웠습니다.

## 8. 현재 시점 면접에서 말할 1분 답변

"LG전자 협업 프로젝트에서 PDF를 Markdown으로 변환해 LLM이 활용 가능한 문서 데이터로 만드는 작업을 했습니다. 당시 문서 구조가 손실되면 AI가 문맥을 정확히 이해하기 어렵다는 점을 경험했고, 이 문제의식이 RAG에 관심을 갖게 된 계기였습니다. 이후 사용자가 업로드한 기술 문서에서 근거 기반 면접 질문을 생성하는 DocuMentor를 개발했습니다. 핵심 기능을 구현한 뒤에는 기본 청킹 방식이 문서 구조를 충분히 반영하지 못하고, 인메모리 저장 구조가 운영 환경에서 취약하다는 문제를 발견했습니다. 현재는 문서 구조 기반 청킹, 검색 품질 지표, 영속 벡터 저장소와 작업 상태 관리로 개선 범위를 정의하고, 기능 구현을 넘어 품질을 측정하고 운영할 수 있는 RAG 시스템으로 고도화하고 있습니다."

## 9. 고도화 완료를 위한 실행 계획

### 최종 목표

문서 업로드부터 질문 생성까지의 RAG 흐름을 재현 가능하게 평가하고, 서버 재시작과 실패 상황에서도 데이터와 작업 상태가 유지되는 서비스로 완성한다. 최종 결과물은 기능 코드뿐 아니라 평가 데이터셋, 개선 전후 측정 결과, 장애·실패 사례 기록을 포함한다.

### 완료 기준

아래 다섯 가지를 모두 만족하면 "고도화했다"고 말할 수 있다.

| 완료 조건 | 산출물 | 확인 방법 |
|---|---|---|
| 검색 품질을 수치로 설명할 수 있음 | Golden dataset, 평가 실행 결과 | 동일한 질의셋에서 Recall@K와 출처 일치율 측정 |
| 문서 구조를 보존한 청킹이 적용됨 | 문서 유형별 splitter와 메타데이터 | 제목·페이지·코드 블록이 보존된 청크 확인 |
| 검색 개선 효과가 있음 | 개선 전후 비교표 | baseline 대비 정한 핵심 지표의 개선 확인 |
| 서버 재시작 뒤에도 검색 가능 | 영속 벡터 DB와 재기동 검증 기록 | 재기동 후 기존 문서로 질문 생성 성공 |
| 생성 실패를 추적·재시도 가능 | DB 기반 generation job, 재시도 API | 실패 사유 확인 및 재시도 후 상태 전이 검증 |

### 1단계. Baseline과 평가셋 만들기

**목적:** 이후의 모든 개선을 감이 아닌 비교 가능한 결과로 판단한다.

- 대표 문서 5~10개를 선정한다. Markdown 중심 문서, PDF 중심 문서, 코드 블록이 많은 문서를 섞는다.
- 문서별로 평가 질문 5개 내외와 정답 근거 위치(페이지 또는 섹션)를 직접 작성한다.
- 현재 구현으로 질문별 검색 top-K 결과를 저장한다.
- 아래 지표를 산출한다.
  - Recall@K: 정답 근거 청크가 상위 K개 검색 결과에 포함된 비율
  - 출처 일치율: 생성 질문의 출처가 사람이 지정한 근거와 일치하는 비율
  - 중복 질문 비율: 같은 의미의 질문이 반복 생성된 비율
  - 생성 실패율: 질문 생성 요청 중 실패하거나 근거가 부족해 제외된 비율

**완료 산출물:** `docs/rag-evaluation/golden-dataset.md`, baseline 결과 CSV 또는 JSON, 결과 요약 문서.

### 2단계. 문서 구조 기반 청킹 적용

**목적:** 질문 생성에 필요한 근거가 한 청크 안에 자연스럽게 유지되도록 한다.

- Markdown은 heading을 우선 경계로 사용하고, 하위 문단은 길이에 따라 재분할한다.
- PDF는 페이지 정보를 유지하면서 문단 단위 분할을 우선 적용한다.
- 코드 블록과 표는 중간에서 잘리지 않도록 별도 처리한다.
- 모든 청크에 `userId`, `documentId`, `page`, `sectionTitle`, `chunkIndex`, `fileType` 메타데이터를 저장한다.
- overlap 크기를 2~3개 후보로 실험하고, 1단계 평가셋에서 가장 좋은 조합을 선택한다.

**완료 기준:** baseline 대비 Recall@K 또는 출처 일치율 중 하나 이상이 개선되고, 코드 블록·제목 경계가 깨지는 대표 실패 사례가 감소한다.

### 3단계. 검색 전략 고도화

**목적:** 사용자 설정값을 단순 나열하는 대신, 실제 질문 생성에 필요한 근거를 더 정확히 찾는다.

- 분야·난이도·질문 유형을 검색 목적이 드러나는 자연어 질의로 재구성한다.
- top-K와 similarity threshold 조합을 실험한다.
- 동일 문서·인접 청크가 과도하게 반환되는 경우 중복 제거를 적용한다.
- 필요할 경우 후보 청크를 넓게 검색한 뒤 reranking해 최종 컨텍스트를 선별한다.
- 검색 점수와 선택된 청크 정보를 로그 또는 DB에 남겨 실패 사례를 분석한다.

**완료 기준:** 1단계의 동일 평가셋에서 검색 지표와 중복 비율을 개선 전과 비교해 기록한다. 개선 효과가 없는 기법도 실험 결과와 함께 제외 사유를 남긴다.

### 4단계. 영속 벡터 저장소 및 데이터 정합성

**목적:** 프로토타입 구조를 실제 운영 가능한 구조로 전환한다.

- `SimpleVectorStore`를 pgvector 또는 Qdrant로 교체한다. 현재 MySQL을 사용 중인 구조와 별개로 벡터 검색 전용 저장소를 둔다.
- 문서 업로드·삭제·재색인 시 벡터 데이터도 함께 생성·삭제·갱신되도록 한다.
- 사용자와 문서 ID 필터를 모든 검색에 적용해 다른 사용자의 문서가 검색되지 않도록 한다.
- 애플리케이션 재시작 후 기존 문서를 대상으로 질문을 생성하는 통합 테스트를 작성한다.

**완료 기준:** 재기동 후 기존 인덱스로 질문을 생성할 수 있고, 문서 삭제 뒤 해당 문서 청크가 검색되지 않는다.

### 5단계. 생성 Job 영속화와 실패 복구

**목적:** 긴 시간이 걸리는 LLM 요청을 상태 추적 가능하고 복구 가능한 작업으로 관리한다.

- 메모리 기반 생성 상태 관리 구조를 `question_generation_jobs` 테이블로 이전한다.
- Job에 상태, 시작·종료 시각, 실패 사유, 재시도 횟수, 요청 조건을 저장한다.
- 상태를 `PENDING -> RETRIEVING -> GENERATING -> COMPLETED | FAILED`로 명확히 정의한다.
- 실패 Job 재시도 API와 프론트엔드 재시도 동선을 제공한다.
- LLM API 오류, 검색 결과 부족, 파싱 오류를 구분해 사용자 메시지와 운영 로그에 남긴다.

**완료 기준:** 서버 재시작 뒤에도 Job 조회가 가능하고, 의도적으로 발생시킨 실패 Job의 원인을 확인한 뒤 재시도할 수 있다.

### 6단계. 최종 검증과 포트폴리오화

**목적:** 구현 경험을 채용 과정에서 설명 가능한 근거로 완성한다.

- 동일 Golden dataset으로 개선 전후 결과를 측정한다.
- 최소 3건의 실패 사례를 "현상 - 원인 - 조치 - 결과" 형식으로 기록한다.
- RAG 구조도, 데이터 흐름, 평가 결과 표를 README 또는 포트폴리오 문서에 추가한다.
- 수치는 문서 수, 평가 질문 수, K 값, 모델 및 임베딩 모델, 측정 날짜를 함께 남긴다.

**완료 산출물:** 개선 전후 지표 표, 실패 사례 문서, 통합 테스트, 아키텍처 다이어그램, 최종 README.

### 권장 일정

| 기간 | 핵심 작업 | 끝났다고 판단할 수 있는 결과 |
|---|---|---|
| 1주차 | 평가셋·baseline | 현재 성능을 숫자로 설명 가능한 상태 |
| 2주차 | 구조 기반 청킹 | 청킹 개선 전후 검색 결과 비교 |
| 3주차 | 검색 질의·reranking 실험 | 선택한 검색 전략과 제외한 전략의 근거 |
| 4주차 | 영속 벡터 저장소 | 재기동·문서 삭제·재색인 검증 |
| 5주차 | Job 영속화·재시도 | 실패 추적과 복구 동작 검증 |
| 6주차 | 통합 테스트·문서화 | 지표, 실패 사례, 아키텍처를 갖춘 포트폴리오 |

### 구현 우선순위

시간이 부족하면 1단계, 2단계, 4단계를 먼저 완료한다. 이 세 가지는 "문서 구조를 반영해 검색 품질을 개선했고, 서버 재시작 후에도 안정적으로 동작하도록 고도화했다"는 가장 강한 완료형 서사를 만든다. Job 영속화는 백엔드 운영 역량을 강조하고 싶을 때 다음 우선순위로 진행한다.

## 10. 고도화 완료 후 면접에서 말할 1분 답변

"LG전자 협업 프로젝트에서 PDF를 Markdown으로 변환해 LLM이 활용 가능한 문서 데이터로 만드는 작업을 했습니다. 당시 문서 구조가 손실되면 AI가 문맥을 정확히 이해하기 어렵다는 점을 경험했고, 이 문제의식이 RAG에 관심을 갖게 된 계기였습니다. 이후 사용자가 업로드한 기술 문서에서 근거 기반 면접 질문을 생성하는 DocuMentor를 개발했습니다. 초기 구현 후에는 토큰 단위 청킹이 문서 구조를 충분히 반영하지 못하고, 인메모리 저장 구조가 운영 환경에서 취약하다는 문제를 발견했습니다. 이를 해결하기 위해 문서 구조 기반 청킹과 검색 품질 평가셋을 구축하고, 검색 전략을 실험해 근거 일치율과 중복 질문 비율을 개선했습니다. 또한 영속 벡터 저장소와 DB 기반 생성 Job을 도입해 서버 재시작 후에도 기존 문서 검색과 작업 상태 추적이 가능하도록 고도화했습니다. 이를 통해 RAG를 단순 LLM 연동이 아니라 데이터 전처리, 검색 품질, 운영 안정성을 함께 설계해야 하는 시스템으로 이해하게 되었습니다."

> 위 답변의 "개선했습니다" 부분에는 6단계에서 측정한 실제 수치만 넣는다. 예: "근거 일치율을 A%에서 B%로 개선했습니다."

## 11. 기록 원칙

- 이미 구현한 기능은 완료형으로 작성한다.
- 아직 진행 중인 개선은 "발견했다", "설계했다", "개선 중이다"처럼 사실에 맞게 작성한다.
- 성과 수치는 개선 전후를 같은 평가셋으로 측정한 뒤에만 기재한다.
- 수치가 나오면 "근거 일치율 A%에서 B%", "중복 질문 비율 A% 감소"처럼 측정 조건과 함께 기록한다.

## 12. 한 줄 프로젝트 소개

DocuMentor는 PDF·Markdown·TXT 기술 문서를 기반으로 면접 질문을 생성하는 서비스이며, 문서 전처리 경험에서 출발해 청킹·검색·생성·평가 단계의 품질을 개선하고 운영 가능성을 높이는 RAG 학습 서비스다.
